# 评分来源与提交证据

## 1. 不假设权重

先从当前题包、比赛页面或当前工具允许访问的官方接口核对。记录原文/返回字段、赛事 ID、时间和来源。拿不到就标为未知，并按模块缺口和可检出错误推进；不得默认四项各 25%，也不得沿用练习赛的 40%/30%。

历史记录：2026-11-15 contest 35 的技能旧记录记载 `scoringWeights` 四项各 25、两题各 50%。本次复盘没有重新取得当场 API 原始响应，因此它是历史规则记录，不是本次重新核验结果，更不是其他赛事默认值。页面未展示权重不代表接口在所有环境都可访问；遵守实际工具能力与权限。

固定顺序“方法→行→分支→变异”也不能由相同权重推出。先有带断言的模块覆盖，再按边际检出、缺口、耗时调整。报告区分：
- METHOD、LINE、BRANCH 的 covered/total；
- LINE 仅为行覆盖代理，不冒充平台 statement；
- KILLED/全部变异及其他状态，detected 单列；
- 平台成绩及未知的评分转换。

## 2. 下载

用户已下载时直接核对本地原包。否则使用当前工具支持的下载能力、当前已观察的附件入口；保留 ZIP 哈希，验证解包路径和文件名编码。

历史接口 `GET /api/contests/{id}` 曾返回附件信息，文件 URL 接口曾返回短期预签名地址。这是定位线索，不是可直接复用的稳定 API 合约；不猜测 URL、不保存令牌、不因接口不可用阻塞可完成的本地工作。编码异常先确认原条目，不反复覆盖解压。

## 3. 上传是一次有明确版本的操作

用户授权提交后，核对当前赛事/题目、槽位、大小和冻结文件哈希；浏览器操作依当前工具文档，不预设插件或未支持 API。

历史前端观察到“选择文件→提交→上传→确认”步骤，但不能把“选择文件永远不发送请求”当安全保证。以当前页面状态区分待选、上传中、已提交、失败。提交中不重复点击；失败先确认平台是否已接受，再决定重试。

## 4. 回执的证据强度

| 证据 | 能说明什么 | 不能说明什么 |
| --- | --- | --- |
| 页面已提交/2个文件 | 平台存在记录 | 本会话上传了当前版本 |
| 文件名、大小、submittedAt | 与本次操作是否相符 | 内容字节一致；同大小可不同内容 |
| 本次上传调用结果 + 文件哈希 + 页面回执/提交ID | 绑定本次操作和本地版本 | 平台重新编译/评分结果 |
| 平台提供下载或校验和，且字节/哈希一致 | 可进一步核验服务端材料 | 未出分时的正式成绩 |

接口允许时补查 submittedAt、文件名和字节数；没有接口就保存可取得的页面回执，准确说明证据范围。不要为拿不到更强校验而虚构“最强一致性”，也不要反复上传当验证。

## 5. 多会话收尾

同一账号多个工具可能重交。提交前对照最近记录、共享交付清单和用户指定的收尾者。发现更新但来源不明的版本时，先查本地各交付件/日志；仍无法判断且覆盖会丢失他人成果时，说明冲突并请求用户指定最终版本。已有明确收尾授权则按该授权执行，不重复问同一权限。

禁止“最后再交一次夺回本会话版本”。最后一次计分是平台规则，不是让多个代理互相覆盖的策略。保底提交仅在授权、截止安排和版本可验证时采用，不能宣称任何新版本都优于现有版本。

## 6. 时间

以当前明确的截止时间及时区为准，不用向下取整倒计时反推。赛前页面未开放时到开始点刷新即可，不重复登录。估算收尾余量使用本轮构建/上传耗时；过期、评分中、未取得结果分别报告。
