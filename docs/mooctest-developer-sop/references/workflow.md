# 从项目到提交的操作流程

## 1. 打开项目与保存基线

1. 默认当前目录及其所属仓库为工作区，用户另有指定则使用指定目录。读取适用的 AGENTS.md、说明、示例和 POM。识别聚合 POM 与模块，进入对应题目执行。
2. 比对页面工程名、附件名、包名与源码，避免混淆不同赛题。保留原始题包。
3. 执行 `java -version`、`mvn -version`，检查真实 Java home。优先遵循项目提供的 Maven Wrapper，缺少环境时报告具体缺项，不预设安装位置。
4. 在工程外保存 POM、src/main 的相对路径清单及 SHA-256，最终比较以发现修改、新增和删除。已有改动先记录，不把已改版本自动当官方原版。
5. 识别旧报告、多测试类、被禁用测试、插件与依赖。是否执行基线测试取决于本次运行轮数约束，不先跑再确认。

## 2. 编写单文件测试

- 按方法、构造、状态转移、短路条件列正常/边界/异常场景，写独立预期值，仅选择适用于 API 的输入。
- 全部放入原包的 src/test/java/.../xxxTest.java，类名与文件名一致，采用 Jupiter 注解。优先同顶层类辅助方法，不新增依赖或独立辅助源文件。
- 合并旧多类测试时检查导入、生命周期、重名方法、静态状态和清理；合并后完整验证，不能只上传不能独立编译的入口。
- 断言结果内容、顺序、边界、异常类型、状态变化；必要时用小规模穷举参照或固定序列。避免仅断言不抛异常、复制被测算法或依赖随机/真实时间。
- 反射按当场许可，优先公开 API；不破坏对象不变量、不探测变异环境制造杀死结果。
- 疑似业务缺陷区分需求期望与实现刻画，单独记录依据/复现/实际结果；不改源码，不把刻画测试当成需求正确性证明。

## 3. 运行与分析

读取原工程插件后选择命令。已配置 Surefire 与 PIT 的 Maven 项目可参考以下命令；使用 Wrapper 时替换入口，先检查插件配置：

```powershell
mvn test
mvn org.pitest:pitest-maven:mutationCoverage
```

若用户限定一个手工执行轮次，可写完后一次调用 `mvn test org.pitest:pitest-maven:mutationCoverage`；PIT 自身会重复运行测试。编译失败也如实记录执行阶段，不隐瞒重试。不修改 POM，不覆盖评分目标、算子或排除类，不用 skip 绕过检查。

正常迭代：JUnit 成功 → 查 JaCoCo 分支缺口 → 查 PIT 存活项 → 有依据补测 → 再验证。每轮记录测试/源码哈希、命令、时间、退出码和报告路径。最终改过代码必须重新验证，不能沿用旧报告。

| 检查 | 证据 |
| --- | --- |
| 测试发现和通过 | Surefire 汇总及 target/surefire-reports；发现数大于 0，失败/错误为 0，跳过项有说明 |
| 分支覆盖 | target/site/jacoco/jacoco.xml 的 BRANCH covered/(covered+missed)，或 HTML 分支列 |
| 行覆盖 | JaCoCo LINE 或 PIT Line Coverage，禁止称为分支覆盖 |
| 变异杀死 | target/pit-reports 最新报告，保留分子/分母、状态及原始算子/目标范围 |
| 版本一致 | 报告时间、类集合和测试版本对应，HTML 及依赖资源完整 |
| 修改边界 | 源码/POM 清单和哈希与基线一致 |

XML 未生成时先读原配置现有报告，不为方便采集修改 POM。TIMED_OUT、RUN_ERROR 等保留状态，不全部声称为断言杀死；自算指标注明口径。

中文路径造成 JaCoCo 缺失时先查实际本轮数据；只重新生成报告时说明未重跑测试，不能冒用上轮数据。若使用 ASCII 路径副本，核验源码/POM/测试一致，保存路径映射。

若该环境已经验证存在路径编码问题，可在检查原 argLine 后，用同版本 JaCoCo agent 的相对输出 `destfile=target/jacoco.exec` 预防。动态解析 agent 位置，保留原有必要 JVM 参数，不改 POM、目标和算子。成功时直接核验本轮报告，不再执行查找乱码目录和单独生成报告的恢复步骤，详见 [已验证的精简方案](testing-methodology.md#11-减少重复操作的经过验证方案)。

SURVIVED 逐项分类为缺输入、缺断言、未覆盖、等价/冗余。可区分则补测，等价则记录位置、算子和输入分类证明；覆盖到不代表杀死。不缩小分母、不改报告。无新假设时停止空跑，交付真实指标及限制。

## 4. 打包与验收

在工作区创建独立交付目录，例如 deliverables/<题目>/<版本>/，与打包源目录分开。源项目位于工作区根时显式排除交付目录，避免 ZIP 递归打入自身。这是组织建议，不是官方命名要求。

两个必需产出：

1. xxxTest.java：UTF-8，与工程内测试字节一致，满足页面 ≤2.0 MB。
2. 完整项目 ZIP：满足 ≤20.0 MB，含原 POM、src/main、单测试文件、必要配置/资源、执行后的 target；保留题包原有 wrapper 等构建文件。

明确选取本题文件，排除 .git、其他题、编辑器缓存、个人文件和嵌套提交包。不能只用 git archive，它会漏掉忽略的 target。报告包含 HTML 及必要资源，不只首页。

列出 ZIP 条目检查必需文件、测试数量、目录层级和误包；解压到新临时目录，比对源码/POM/测试哈希和报告完整性。允许额外执行时可在副本复跑；限定一次时只静态验包，不暗中再跑。

超限先查误包和历史报告；不擅删必需 target 或改变统计范围。仍超限时保留材料，核实允许精简方式。

ZIP 外使用 [交付记录模板](../assets/delivery-record.md)写清单：文件名、工作区相对路径、字节数、SHA-256、源码/测试版本、命令、通过数、覆盖/变异分子分母、报告路径、基线比较。内部日志和分析不自动作为赛事附件上传。
