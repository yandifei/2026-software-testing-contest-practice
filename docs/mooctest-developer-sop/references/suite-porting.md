# 同题套件移植与合并

适用：手上有两份及以上针对**同一题包**的测试文件（旧版本、他人产出、另一条执行线、历史交付），需要判断能否合并、怎么合并、合并后凭什么验收。用户要求"独立重写"时走 [独立重做](independent-rebuild.md)，不得用本文绕过。

## 1. 先判同源，再谈移植

逐项核对，全部满足才允许移植断言：

| 判据 | 做法 |
| --- | --- |
| 生产源码同源 | 分别用 `scripts/baseline.py` 生成 `src/main` + `pom.xml` 的 SHA-256 清单后比对，不看目录名、项目名或修改时间 |
| 构建配置同源 | POM 逐字节相同（含 parent、插件版本、mutator、argLine、surefire 发现规则） |
| 测试落点一致 | 单文件路径、包名、类名与当前题包要求一致 |
| 基线未被污染 | 任一方都不曾改动生产代码；有改动先恢复到可信题包 |

不满足时只借"缺口定位、候选输入、证明思路"作研究线索，不直接搬运断言：上下文、单位、舍入和契约可能不同（见 [并行集成](multi-agent-integration.md) 第 8 节）。

## 2. 体量不是强度

2026-11-15 省赛实测：两工程 `src/main` 与 `pom.xml` 逐字节相同，只有测试文件不同（完整记录见 [合并增强线](case-2026-11-15-merge-sweep.md)）。

| 套件 | 行数 | 测试数 | JaCoCo 行 | JaCoCo 分支 | PIT KILLED |
| --- | --- | --- | --- | --- | --- |
| A（"完整"套件） | 4516 | 350 | 72.67% | 79.80% | 1722/2528 |
| B（短套件） | 893 | 49 | 79.98% | 83.94% | 1725/2528 |
| A∪B（合并） | — | 399 | 88.44% | 91.27% | 2058/2528 |

A 的测试数是 B 的 7 倍，行/分支覆盖反而更低。**先量后选**：各自跑一轮 JaCoCo + PIT，按包比较缺口，再决定"以谁为骨架、把谁搬过来"。文件大小、创建时间、谁先写、看起来更规范，都不是证据。

### 2.1 三份以上候选：先冻结重跑，再按击杀选

2026-11-16 同一题包下有三份来自不同模型的套件（`src/main` 与 `pom.xml` 三方逐字节相同）。三份报告都曾过期或截断，因此全部冻结后重跑，得到同口径数据（完整记录见 [三方合并案例](case-2026-11-16-cross-ai-merge.md)）：

| 题 | 候选 | 行数 | 用例 | 分支 | PIT 检出 | 选择 |
| --- | --- | --- | --- | --- | --- | --- |
| card | GPT/rewrite | 652 | 32 | 89.27% | 1123/1320（85%） | 否 |
| card | deepseek | 8998 | 247 | 99.30% | 1285/1320（97%） | **骨架** |
| card | GLM | 9781 | 815 | 99.16% | 721/1320（55%） | 只取独有边界 |
| math | GPT/rewrite | 7573 | 506 | 95.94% | 2061/2528（82%） | 否 |
| math | deepseek | 13058 | 575 | 98.35% | 2422/2528 | **骨架** |
| math | GLM | 13941 | 1084 | 98.42% | 2106/2528（83%） | 只取独有边界 |

两条硬规则：
- **不按用例数/行数/“分支最高”选骨架**。GLM 的 card 分支 99.16% 但击杀只有 55%，说明用例多而断言弱；按分支选会丢掉约 564 个可继承击杀。
- **候选文件必须冻结**。本轮分析期间 `deepseek/math-assessment` 的测试文件仍被另一条执行线修改（15:48），活动目录不能作为“当前最强”的依据。

### 2.2 旧“等价清单”只当假设

上一轮报告里的“剩余 N 条全部等价”是待复验的假设，不是资产。本轮继承的 35 条中，至少 7 条被真实输入杀死：

| 旧标签 | 反例输入 | 命中的等值点 |
| --- | --- | --- |
| Maestro `checkLength` 边界等价 | 12 位与 19 位、合法 IIN | `>=12` 与 `<=19` 两个等值点 |
| MaestroUK `checkLength` 边界/恒真等价 | 12/19 位合法、11/20 位越界 | 长度窗口上下界 |
| Luhn `for(i=1;i<size;i+=2)` 等价 | 19 位 Luhn 合法串 | 奇数长度时 `<=` 会越界 |

复攻顺序固定：等值点 → ±1 → 长度上下界 → 奇偶 → 空/空白/null → 构造器边界。给不出反例时，写“已攻击未证明”，不要写“等价”。

## 3. 合并步骤（可脚本化，但每步都要验）

1. **冲突扫描**：`python -B scripts/member_conflicts.py <主文件> <被移植文件>`，按"类体深度 1"提取成员名并报告交集，返回码 1 表示有冲突。它比较的是**名字**（去重后的名字数，不区分参数列表），所以同名重载也会被报出来——这是保守误报，人工确认签名不同即可放行。真冲突（同签名方法、同名字段/嵌套类）必须先改名或删其一：同签名方法会被静默覆盖，同名类会被静默遮蔽，未必编译失败。需要连跑合并时可用 `merge_engine.py --check-conflicts`，冲突即拒绝并返回 1。
2. **导入并集**：保留两边 import 去重；同一个简单类型来自不同包时改全限定名，避免歧义。原文件大量使用全限定名的风格可以直接沿用，比合并 import 更安全。
3. **插入位置**：把被移植文件的**类体内容**（不含 `package`/`import`/类声明/文件末尾 `}`）插到目标类最后一个 `}` 之前。
4. **结构自检**：插入后按花括号深度确认插入点深度为 1（确实在类体内），且文件末尾只有唯一顶层 `}`。字符串、注释、text block 里的花括号会骗过朴素计数，不能只看"脚本退出 0"。
5. **立即真编译**：先 `mvn -B test`，不要直接跑 PIT。编译期会暴露 mock 返回类型、断言重载歧义、注解目标、被注册对象的构造合法性。
6. **全量验收**：JUnit 全绿 → JaCoCo → 全量 PIT，三者对应同一测试文件哈希。
7. **身份对账**：`python -B scripts/mutation_union.py --provider 合并版=... --provider 被合并版=... --baseline 合并版`。合并前后若出现“被合并版杀、合并版没杀”，说明插入不完整或被后续编辑覆盖；按 `killingTest` 名字回到源文件补齐。

## 4. 平铺还是 `@Nested`：先看 static 与钩子

两种形态都能运行，选错会直接编译失败或悄悄改变行为。逐项过：

| 条件 | 形态 |
| --- | --- |
| 工具链 JDK ≤ 15，且被移植段含 `static` 成员（字段、方法、内部类；常量除外） | 只能平铺：JDK 15 及以前非静态内部类不允许 static 成员，编译失败 |
| 外层类有会改全局状态的 `@BeforeEach/@AfterEach/@BeforeAll` | 优先平铺；用容器要逐个评估钩子对被移植段的副作用 |
| 题包或 Surefire 配置不接受嵌套测试类 | 只能平铺 |
| 以上都不成立，且希望成员名彼此隔离 | 可用容器 |

**注意版本**：JDK 16 起（JEP 395）已放开"内部类不能声明 static 成员"的限制。因此在 JDK 17/21 题包里，把含 `static` 成员的套件包进 `@Nested` **不会**编译失败——没有编译器兜底，形态只能靠判断，不能靠"跑一下就会炸"。判断前先核对 `java -version`/`mvn -version`（见 [工作流](workflow.md) 第 1 节）。

`@Nested` 隔离成员名称，但**不隔离生命周期**：外层钩子仍会作用到内层。

工具与形态必须对齐：

- `scripts/merge_engine.py` 默认把被移植内容包进 `@org.junit.jupiter.api.Nested`（容器名用 `--nested-name` 或第 4 个位置参数）。它只在"可用容器"的情形能直接跑；不满足时只借它的花括号提取逻辑，改为平铺拼接。加 `--check-conflicts` 会先跑成员名冲突扫描，有冲突直接拒绝。
- `scripts/replace_section.py` 面向"已存在的容器体"做修订替换。平铺模式没有容器可替换，修订必须**从冻结主文件 + 冻结片段重新生成**，不能就地改。
- 无论哪种形态，拼接后都要 `mvn -B test` 真编译，再全量 JaCoCo/PIT。

本次实测（2026-11-15，JDK 21）：被移植套件带 `@BeforeEach/@AfterEach`（会清空全局注册表），容器形态会把钩子串进移植段，**决定性理由是生命周期而非编译**；该套件同时含 `private static` 成员，在 JDK 21 下不构成障碍（原文件里 `@Nested` 类内就声明了 `private static` 字段与方法）。最终采用平铺。

## 5. 合并后必查的跨套件串扰

| 现象 | 真实原因 | 处理 |
| --- | --- | --- |
| 断言"缺依赖应失败"的用例不再失败 | 另一套件先注册了该依赖，全局 map 未被任何钩子清理 | 用例内用真实 unregister API 显式清理后再断言 |
| `register(x, true)` 返回值与预期相反 | `getInstance(name)` 内部已自动注册，`containsValue` 命中 | 先读实现；需要"同值不同实例"时先 unregister |
| 单跑绿、全量红（顺序敏感） | 静态缓存、共享池、时钟、单例 | 显式初始化/清理，`finally` 恢复 |
| 顶层测试被算到某个 `@Nested` 行 | Surefire/JUnit5 的归属展示方式 | 看总数与失败数，不按行名判断插入位置 |
| 全量 PIT 变慢并出现 minion 超时 | 测试数增长、并行构建抢 CPU | 见 [研究](coverage-mutation-research.md) 第 11 节的分层反馈 |
| 新增用例没有带来新增击杀 | 同 identity 的变异已被现有用例杀死（本轮数学 5 条新用例多数与 `ResidualAttacks` 重叠） | 写之前按 `killingTest` 反查身份；新增用例至少要覆盖一个此前无杀手的 identity |

## 6. 收益与成本

- 收益只能由**变异身份集合**计算（键见 [并行集成](multi-agent-integration.md) 第 8 节）。按包逐项取最大值再相加，得到的是**下界**，不是上限。
- 成本随测试数增长：同题实测全量 PIT 从 49 测试的约 6 分钟，到 399 测试的约 8.5 分钟、506 测试的约 19 分钟（含 minion 超时重试）。合并后要为最终全量验证预留时间。
- 合并 ≠ 每个套件各自的最优：可能引入状态干扰、重复执行或时间问题。合并后必须重新全量验证，不能把"两套各自绿"当合并结论。

## 7. 验收与表述

- 只认合并后**一次**完整运行的结果；拼接后未重跑不算。
- 三份报告（JUnit/JaCoCo/PIT）必须对应同一测试文件哈希；测试一改，旧报告立即失效。
- 合并版要明确标注构成（原套件 + 移植段），不能冒充独立重写，也不能宣称"并集上限已达到"。

## 8. 合并验收清单（一次过完，别分散找）

1. 同源四项判据通过（第 1 节），两份测试文件哈希已冻结。
2. `scripts/member_conflicts.py` 报告 0 冲突；有冲突则已改名并记录映射。
3. 插入点花括号深度为 1，文件末尾唯一顶层 `}`；UTF-8；单文件路径符合题包要求。
4. `mvn -B test` 全绿，发现数 = 期望值（按 Surefire 实际发现统计，不按注解数推算）。
5. JaCoCo 报告与当前测试哈希对应，METHOD/LINE/BRANCH 三列都记录。
6. 全量 PIT 独占机器跑完；严格解析后 KILLED/SURVIVED/NO_COVERAGE/TIMED_OUT 分列，各状态之和 == 总数。
7. `scripts/verify_baseline.py` 确认 `src/main` 与 `pom.xml` 未变、`src/test` 只有一个测试文件。
8. 按变异身份集合对账新增/丢失（`scripts/mutation_union.py --baseline 合并版`）；丢失项要解释，“总数没降”不等于“没有回退”。同一身份在别家报告里是 KILLED 时，按 `killingTest` 反查是否删了用例——合并版自称的“等价清单”不能当证据。
9. 三份报告与命令/退出码/哈希保存到项目外，作为本轮证据。
10. 三份以上候选：每份测试文件哈希已冻结，报告 mtime ≥ 测试 mtime，且总数 == 各自控制台 `Generated`；任何一份不新鲜就重跑后再比较。
11. 继承的等价/不可达清单已做边界复攻并记录反例；没有反例的条目写"已攻击未证明"，不写"等价"。
12. 新增用例已按 `killingTest` 反查，确认至少命中一个此前无杀手的变异身份；否则合并或删除。
