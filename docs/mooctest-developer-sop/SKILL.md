# 慕测开发者测试

以当前目录及其所属仓库为工作区，按用户指定题目和阶段完成任务。支持核对规则、编写测试、验证、打包或完整提交，不将局部请求扩大为提交。

## 开始执行

1. **先打开浏览器、登录并下载题目。** 在 Codex（ChatGPT）、Claude、WorkBuddy 等 AI 编程工具提供的浏览器界面中，按 [登录、选赛与下载](references/browser-entry.md)进入慕测登录页，让用户自行输入凭证并登录；再进入比赛列表，滚动到底部查找目标比赛，点击进入并下载题目。已有登录态、比赛页或题包时复用，不重复登录或覆盖已有项目。只处理现有本地项目且不需要下载时，可直接进入下一步。
2. 读取 [赛事规则](references/competition-rules.md)，获取当前比赛页和下载题包要求，记录年份、阶段、题目、截止时间、代码边界、上传格式和大小。参考资料是带日期的规则快照，不能替代当场规则。
3. 以当前目录及仓库为工作区，解压并核对题包。读取适用的 AGENTS.md、项目说明、pom.xml 和示例测试。存在多个项目时，按题目、附件名与网页工程名匹配；无法唯一匹配才询问。路径从工作区解析，不预设盘符、用户名、IDE 或工具安装位置。
4. 按请求执行以下阶段；未限定轮数时，允许针对明确缺口迭代。用户限定次数时遵守，不额外先跑基线。

## 编写与验证

读取 [测试工作流](references/workflow.md)第 1–3 节。

### 使用 Superpowers 等测试技能

编写测试前，检查当前环境可用的技能并实际读取相关说明，优先结合 Superpowers 提高用例质量、分支覆盖率和变异杀死率：

- 开始工作时读取 `using-superpowers`，按其要求选择适用技能。
- 设计用例时使用测试质量指导，例如 `test-driven-development` 随附的 `writing-good-tests`，或可用的 `tdd` 技能：先说明每个测试应检出的错误，再设计独立预期值、边界矩阵、异常路径和状态断言。不得让被测代码同时计算预期值。
- 编译失败、测试失败、报告异常或指标出现意外缺口时，使用 `systematic-debugging`：先读取证据并定位原因，再提出单一假设、做最小修正并验证，避免盲目追加用例或反复重跑。
- 宣称通过、达到某个覆盖率或准备提交前，使用 `verification-before-completion`，以本轮实际执行和报告为依据。

技能可能以 `superpowers:` 前缀或无前缀提供，按当前技能目录发现，不写死安装路径，也不假设接收者已安装。相关技能不可用时，采用本技能自带的 [测试方法与故障处理](references/testing-methodology.md)，如实说明未加载外部技能，不阻断可完成的测试工作。

本赛事禁止修改生产代码，因此不执行 TDD 中修改或删除被测实现的步骤；对既有实现采用回归测试、独立参照与 PIT 验证断言敏感性。先依据 JaCoCo 找分支输入缺口，再依据 PIT 找断言缺口；每轮补测必须对应具体缺口或可区分变异。Superpowers 是执行方法，不保证百分比达到 100%，也不能改变赛事约束或统计口径。

### 执行要求

- 禁止修改、删除、替换或新增 `src/main/java/net/mooctest/` 下的被测源代码，也不得移动源文件、改变包名或通过生成步骤覆盖它们。其他被测源码及 `pom.xml` 同样保持原样，只编写允许的测试内容。执行前后对比源码文件清单及哈希，出现差异时不得打包提交，先查明原因并恢复到可信题包基线。
- 按适用规则将测试集中于一个 xxxTest.java，文件名与类名一致，使用 UTF-8 和题包指定的 JUnit。覆盖正常、边界、异常及状态变化，测试独立。
- 用原项目插件运行 JUnit、JaCoCo、PIT，核对测试发现数、成功状态与最终报告版本。
- 区分分支、行覆盖和原始变异杀死率。有输入或断言依据才补测；等价变异记录证明，不改报告、不缩小分母凑满分。

## 打包

读取 [测试工作流](references/workflow.md)第 4 节，使用 [交付记录模板](assets/delivery-record.md)填写结果。

生成独立 Java 文件和完整项目 ZIP，满足当前上传限制，保留要求的执行后 target。检查 ZIP 条目、源码/POM 基线以及独立 Java 与包内测试的字节一致性。交付记录留在 ZIP 外，不自动增加赛事附件。

对于 Research-Project-Management-System 练习题：将所有模块的测试方法集中于一个顶层测试类、一个 `xxxTest.java` 文件；完成验证后，将该题完整项目目录压缩为 ZIP。分别上传该 Java 文件和项目 ZIP，共两个文件。生产代码仍保持原来的多文件结构，不合并。具体依据和目录示例见 [Research 交付要求](references/competition-rules.md#research-交付要求)。

## 提交

用户要求提交对应题目时，读取 [浏览器提交](references/browser-submission.md)，确认赛事和题目，上传同一版本的材料并取得回执。评分未完成则标记评分中。

使用当前环境可用的浏览器控制工具，不预设固定插件。能力不可用时，完成本地可做阶段，交付材料并说明具体阻碍，不把准备完成称为提交成功。

## 验收与汇报

报告实际完成阶段、交付文件、通过数、分支分子/分母、变异杀死数/总数、报告依据、剩余问题及提交回执。本地指标与平台成绩分开。关键规则冲突、源码基线异常或材料无法满足容量时，保留成果并说明具体问题；没有新假设时不反复空跑或重复提交。

需要设计独立判定方法、合并历史测试，或处理覆盖报告/上传工具异常时，读取 [可复用测试方法与故障处理](references/testing-methodology.md)。新增经验必须来自真实观察，写清症状、判断依据、恢复方式与适用边界，不将某台机器的路径或偶发错误固化为通用前提。
