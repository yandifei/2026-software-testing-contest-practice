## 建议的练习工作流

将需求、用例、脚本和证据使用同一编号关联，避免脚本能执行却无法说明验证了哪个需求。

| 环节 | 练习内容 | 自查结果 |
| --- | --- | --- |
| 需求拆分 | 登录、查询、增删改、权限或其他题目实际提供的功能 | 每项有可观察的正确行为 |
| 用例设计 | 正常流程、边界、缺失／错误输入、状态与权限差异 | 写明前置条件、输入和预期 |
| 自动化 | 稳定元素定位、等待页面状态、操作和断言 | 失败指向具体检查点 |
| 证据收集 | 保存关键步骤与实际结果截图 | 截图能对应到用例编号 |
| 清理复跑 | 清理测试数据、退出账号、关闭浏览器 | 再跑一遍不依赖上次数据 |
| 打包演练 | 按题目要求整理文档、代码、截图 | 在干净目录验证后上传 |

自用用例表可采用 `编号 / 需求 / 前置条件 / 数据 / 步骤 / 预期 / 实际 / 结果 / 截图`。这是训练建议，正式比赛若提供模板应采用官方模板。

优先把一个完整业务流程跑稳，再抽取重复页面操作。等待应针对“元素可见、可点击或结果已变化”等条件；固定长时间休眠会拖慢执行，也不保证动态页面已经就绪。学习依据见 [Selenium 等待策略](https://www.selenium.dev/documentation/webdriver/waits/)。
