## 2. 取精华：具体借鉴了什么

### 2.1 card-approval

1. **整体骨架取自 `deepseek`**：247 个用例覆盖 51 个类，含 `CardProbeTests` 反射探针、
   权限矩阵 5 种角色、费用规则 11 个枚举、审批状态机、考勤/加班/请假边界。
2. **从 `glm` 提炼 7 条长度边界用例**（改写为 `CardNetworkBoundaryTests`，修正了 glm 中
   “用 6 位前缀直接断言 validate” 的错误写法）：
   - `MaestroValidator` 12 位 / 19 位（`checkLength` 的 `>=12`、`<=19` 两个等值点）；
   - `MaestroUKValidator` 12 位 / 19 位 + 11 位 / 20 位（`checkLength` 返回恒真变异）；
   - `VerveValidator` 19 位（`<=19` 等值点）；
   - `Validator` + `LuhnValidator` 19 位奇数长度（`for (i=1; i<size; i+=2)` 的 `<=` 变异）。
   - 收益：这 7 条把卡片题从 1286 提升到 **1293**，且其中 4 条是“唯一杀手”。
3. **丢弃 `GPT/rewrite` 的卡片套件**：32 个用例不足以覆盖 1320 个变异，只作为交叉验证参考。

### 2.2 math-assessment

1. **整体骨架取自 `deepseek`**：575 个用例，业务（报名/定价/退款/进度/排课/评分）+ 表达式引擎。
2. **从 `glm` 的排课用例得到两个缺口线索**，补充：
   - `HYBRID` 授课、`roomId = null` 时 `HYBRID_ROOM_REQUIRED`；
   - 周日重复课程 `RECURRING_WEEKEND_SESSION`（原套件只测了周六）。
3. **从 `glm` / 历史附录的“未解决清单”提炼退款窗口等值点**：
   - 恰好 168h 仍命中 `SEVEN_DAY_PARTIAL_REFUND`（70%）；
   - 恰好 336h 仍命中 `FOURTEEN_DAY_PARTIAL_REFUND`（50%）；
   - 恰好 720h 仍命中 `THIRTY_DAY_EXCEPTION`（25%）。
   这三条直接击中 `RefundPolicyService.determineEligibleRate` 的 `<=` 边界。
4. **丢弃 `glm` 的 1084 条中约 1000 条**：与 deepseek 重复、只断言“不抛异常”或不带断言，
   数量翻倍但击杀率下降；只保留其独有边界思想。

### 2.3 本次新增代码的写法（企业命名 + 逐行注释）

新增的两个 `@Nested` 类全部满足：
- 类名/方法名语义化：`CardNetworkBoundaryTests`、`maestroAcceptsMaximumLength`、
  `sevenDayWindowIncludesBoundaryHour`……
- 每个方法 `@DisplayName` 说明业务含义；
- 每一行“构造 / 调用 / 断言”前都有中文行内注释，说明**为什么用这个输入**；
- 断言消息用 `decision.reasons()::toString` 输出上下文，失败即可定位；
- 固定时钟 `CLOCK`、固定日期常量，无 `now()`、无随机、无执行顺序依赖。

## 4. card-approval 为什么不是 100%

### 4.1 分支：14 条不可达（99.30% 已是可达上限）

| 类 | 缺口数 | 不可达原因（构造器不变量/既有缺陷） |
|---|---|---|
| `ExpensePolicy` | 4 | `clientBillable` 与空白 costCenter 互斥；`cap` 最小 100 恒非 0；`switch` 已覆盖 11 个枚举；`MEAL.attendeeCount` 恒 0 |
| `Shift` | 3 | 紧凑构造器里 `crossesMidnight()` 读取尚未赋值的 `end`，任何 `NIGHT` 班次必抛 NPE |
| `AdvancedLeavePolicy` | 2 | `switch` 覆盖全部枚举；`chargedDays ∈ {0, 0.5, 1, …}`，(0, 0.5) 为空域 |
| `TaskPolicy` | 2 | `BLOCKED` 必须有 `startedAt`；`switch` 覆盖全部状态 |
| `ApprovalWorkflowEngine` | 1 | `terminal()` 前置检查已拦下所有非活跃状态 |
| `Validator` | 1 | 月/年只能由同一构造器同时赋值 |
| `VerveValidator` | 1 | 第二个 `for` 与第一个完全相同，循环体恒不可达 |

> 结论：在**不改 `src/main`、不 mock 被测类、不构造非法记录状态**的前提下，1999/2013 是理论上限。

### 4.2 变异：27 条逐条等价/不可达证明

| # | 类.方法 L行 | 算子 | 结论与证明要点 |
|---|---|---|---|
| 1 | `AdvancedLeavePolicy.roundHalfDay L304` | BOUND | `value<=0` 改为 `<0` 仅 `value==0` 不同，原式与 `ceil(0)/2` 都得 0 |
| 2 | 同上 | ORDER_ELSE | 唯一调用点传入 `requestedHours/8.0`，而 `requestedHours>0` 由构造器保证 |
| 3 | `AdvancedLeavePolicy.validateUnit L173` | ORDER_ELSE ×2 | `chargedDays` 只能是 0/0.5/整数，(0,0.5) 为空域，then 分支是死代码 |
| 4 | `ExpensePolicy.allowedAmount L221` | EQUAL_ELSE | `cap = base(≥100) × multiplier(≥1) × 1.5/1.25`，`money()` 后不可能为 0 |
| 5 | `ExpensePolicy.allowedAmount L222` | RET_NULL | 上条死分支内的 return，永不执行 |
| 6 | `ExpensePolicy.validateCategoryRules L293` | ORDER_ELSE | `ExpenseItem` 规定只有 `CLIENT_ENTERTAINMENT` 可带 attendeeCount，MEAL 恒 0 |
| 7 | `ExpensePolicy.validateClaimLevel L107` | EQUAL_ELSE | `ExpenseClaim` 禁止 `clientBillable && costCenter.isBlank()`，该分支不可达 |
| 8 | `AttendancePolicy.evaluate L75` | BOUND | `lateMinutes==60` 时 `<=60 → 0` 与 `else -=60` 都得到 0 |
| 9 | `AttendancePolicy.positiveMinutes L197` | BOUND | `minutes==0` 时两条路径都得 0 |
| 10 | 同上 | ORDER_ELSE | 负值在 3 个调用点分别被 `Math.max(0,…)` / `else=0` / `clockOut≥clockIn` 吸收 |
| 11 | `ApprovalWorkflowEngine.ensureActive L180` | EQUAL_ELSE | 前一行 `terminal()` 已覆盖其余 6 个状态，本条件永不触发 |
| 12 | 同上 L181 | EQUAL_ELSE | 同上 |
| 13 | `OvertimePolicy.evaluate L59` | BOUND | `raw>360` 时 `payable` 已被压到 240 并置 `review=true`，本行不改变结果 |
| 14 | 同上 | ORDER_ELSE | 同上 |
| 15 | `OvertimePolicy.roundDownToHalfHour L92` | ORDER_ELSE | `minutes<30` 时 `minutes - minutes%30 == 0`，与提前 return 相同 |
| 16 | `LuhnValidator.algorithmCheck L62` | ORDER_ELSE | `tempNumber<10` 时 `sumOfDigits(tempNumber)==tempNumber`，两支同值 |
| 17 | `LuhnValidator.algorithmCheck L76` | MATH | `sum+=d → sum-=d`，判定是 `sum%10==0`，而 `(-sum)%10==0 ⇔ sum%10==0` |
| 18 | `Validator.validate L80` | TRUE_RET | `isValid==false` 在上一行已抛异常，可达 return 恒为 true |
| 19 | `VerveValidator.checkIINRanges L53` | BOUND | 第二个循环与第一个完全重复；首个循环已判定 506099–506198 |
| 20 | 同上 L53 | ORDER_ELSE | 同上：变异后第二个循环仍能兜底 |
| 21 | `VerveValidator.checkIINRanges L54` | EQUAL_ELSE | 第一循环失效时第二循环给出相同结论 |
| 22 | `VerveValidator.checkIINRanges L60` | EQUAL_ELSE | 跳过第二循环不影响结果（第一循环已覆盖全部有效 IIN） |
| 23 | `VerveValidator.checkIINRanges L61` | BOUND | 只影响 506198，而它在第一循环已命中 |
| 24 | 同上 L61 | ORDER_ELSE | 同上 |
| 25 | `VerveValidator.checkIINRanges L62` | EQUAL_ELSE | 第二循环的 `==` 恒假（进入时必为 506099–506197） |
| 26 | `TypeChecker.checkType L24` | EQUAL_ELSE | 去掉早退后，循环内 `matchesType` 对非法输入逐个返回 false，末尾仍 `return OTHER` |

> 这 27 条的共同点：删除/替换后，**在公开 API 可达的所有输入上返回值、异常、状态完全一致**。
> 想“杀死”它们只能伪造构造器禁止的状态或替换被测实现，而这两个手段被赛题规则明确禁止。

## 5. math-assessment 为什么不是 100%

最终 109 条未检出（78 SURVIVED + 27 NO_COVERAGE + 4 TIMED_OUT），分布：

| 包 | 未检出 | 说明 |
|---|---|---|
| `expression.engine` | 44 S + 21 NC + 4 TO | 引擎内部防御分支、私有入口；4 个 TIMED_OUT 是死循环变异体（PIT 计为 detected） |
| `grading.service` | 9 S | `money()` 统一 `setScale(2)` 抹平边界差异、等级阶梯兜底等 |
| `refund.service` | 10 S + 1 NC | 手续费率封顶/区间倒挂等值域不可达分支 |
| `pricing.service` | 9 S + 5 NC | 促销/优惠券日期区间倒挂、80%/70% 折扣等值点、裁剪循环零迭代 |
| `enrollment.service` | 2 S | `minimumAge=0` 等被其它合取项蕴含的条件 |
| `progress.service` | 2 S | 非顺序学习时 `previousComplete` 恒 true 等 |
| `scheduling.service` | 2 S | 等值点/重复判断的等价分支 |

> 其中相当一部分已可写出“路径矛盾 → 不可达”或“下游归一化 → 等价”的证明（与 card 同法），
> 但引擎内部仍有少量条目未能在赛程内完成逐条证明，故**不虚报为等价**，原样保留在报告中。
